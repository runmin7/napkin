01 — 전제 지식

Electron이 두 개의 세계라는 것

Electron 앱은 성격이 다른 두 프로세스로 나뉜다. 이 구분을 모르면 코드가 왜 이렇게 쪼개져 있는지 이해할 수 없다.

두 프로세스의 역할
구분실행 주체할 수 있는 일이 앱의 파일
메인 Node.js 파일 읽기·쓰기, 창 만들기, 트레이, 전역 단축키 main.js + src/main/*
렌더러 Chromium 화면 그리기, 사용자 입력 받기. 파일 접근 불가 src/renderer/* → renderer/bundle/*

렌더러는 웹페이지와 같다. 보안상 파일 시스템에 손댈 수 없다. 그래서 화면에서 무언가를 저장하려면 메인에게 부탁해야 하는데, 이 부탁을 전달하는 통로가 IPC이고 그 통로의 문을 preload.js가 정의한다.

왜 메인이 편집 내용을 들고 있는가

이 앱에서 가장 중요한 설계 결정이다. 보통은 화면이 내용을 갖고 저장할 때 넘기지만, 여기서는 메인 프로세스가 편집 중인 내용의 원본을 소유한다. 렌더러는 글자가 바뀔 때마다 전체 내용을 메인에 보낸다.

이유 창이 닫히는 순간에 저장하려면 렌더러에게 "지금 내용 줘"라고 묻고 답을 기다려야 하는데, 그 사이에 창이 파괴되면 답이 오지 않는다. 메인이 미리 들고 있으면 기다릴 것이 없다.

02 — 구조

파일별 역할

한 파일이 여러 일을 겸하지 않도록 나누어 두었다. 고칠 곳을 찾는 순서는 늘 같다 — 아래 표에서 책임을 읽고 그 파일만 연다. 파일을 열었는데 찾던 것이 없다면 나눈 기준이 잘못된 것이니 그 자리에서 파일을 옮기지 말고 어느 책임에 속하는지부터 다시 따져 본다.

빌드 산출물

src/ 아래 화면 코드는 그대로 로드되지 않는다. esbuild가 세 개의 진입점 (editor · settings · preload)을 각각 묶어 renderer/bundle/에 내놓고, HTML과 창 설정은 그 번들만 가리킨다. npm start와 npm run build 앞에 번들 단계가 붙어 있다.

진입점별로 다른 형식으로 묶인다
진입점형식왜
editor · settingsiife화면이 일반 <script>로 읽는다. file://에서는 모듈 import가 막히기 때문
preloadcjs--external:electronsandbox 안에서 require할 수 있는 것은 electron뿐이다. 나머지는 전부 이 파일 안으로 들어가 있어야 한다

왜 <script type="module">이 아닌가 Chromium은 file://에서 모듈 import를 CORS로 막는다. Electron의 loadFile()은 file:// URL을 쓰므로 브라우저처럼 모듈을 그대로 로드할 수 없다. 그래서 소스는 import/export로 쓰되 화면에는 번들로 내려 준다.

주의 빠른메모 실행.bat은 electron을 직접 띄우므로 번들을 만들지 않는다. src/ 아래를 고쳤다면 npm run bundle을 한 번 돌리거나 npm start로 실행해야 한다.

CodeMirror 의존성에 대한 판단

CodeMirror는 유지 관리자가 사실상 한 명이다. 그럼에도 택한 이유는 교체 가능한 자리에 두었기 때문이다. 저장 형식도, 자동 저장도, 목록·검색도 전부 이 앱의 코드가 갖고 있다. 라이브러리가 멈춰도 잃는 것은 마크다운 강조뿐이고, Electron 앱은 번들로 배포되므로 패키지가 사라져도 이미 빌드된 exe는 계속 동작한다.

메모리 Electron 기본 + 열린 메모 1개 + 목록 데이터 Chromium이 대부분을 차지한다. 메모 데이터는 무시할 수준

실패 모드

  • 설정 파일 손상 — 백업에서 복구하고 즉시 정상 파일로 되돌린다. 백업도 못 읽으면 .corrupt로 남기고 사용자에게 알린다
  • 단축키 등록 실패 — 다른 프로그램이 점유한 경우. 설정을 되돌리고 어느 기능의 단축키인지 이름을 붙여 알린다
  • 트레이 생성 실패 — 창 닫기를 종료로 바꾼다. 되살릴 방법 없이 프로세스만 남는 상태를 피하기 위해서다
  • 탐색기에서 메모 삭제 — 시작 시 pruneMissing()이 없는 파일을 가리키는 설정을 정리한다. 탐색 중 만나면 건너뛴다

08 — 확인 절차

고친 뒤 직접 돌려볼 것

  1. 01
    부팅 점검
    npm run smoke — 번들을 새로 만든 뒤 앱을 실제로 띄워 window.api·편집기·메모 로드까지 확인하고 스스로 끝난다. 창은 뜨지 않는다. 구조를 건드렸다면 이것부터 돌린다. preload나 번들이 깨지면 앱은 조용히 먹통이 되는데, 그 조용한 고장을 잡는 것이 이 점검이다
  2. 02
    문법 검사
    node --check 를 고친 파일마다. 메인 프로세스 전체는 node -e "require('./src/main/ipc')" 로는 안 되고(electron 모듈이 필요하다) npm start로 확인한다
  3. 03
    앱은 사람이 직접 실행한다
    빠른메모 실행.bat 또는 npm start를 터미널에서 직접. 패키지 앱(MSIX) 컨테이너 안에서 실행하면 %APPDATA% 쓰기가 다른 폴더로 우회되어 메모가 엉뚱한 곳에 쌓인다 (09장 참조)
  4. 04
    저장이 실제로 되는지
    메모를 쓰고 다른 창을 한 번 클릭 → %APPDATA%\빠른메모\notes에 파일이 생기고 창 하단에 저장 시각이 찍히는지
  5. 05
    목록 순서가 튀지 않는지
    Ctrl+PageUp/PageDown으로 메모를 여러 번 오간다. 내용을 고치지 않았는데 순서가 바뀌면 flushDraft()의 내용 비교가 깨진 것이다
  6. 06
    패널 너비 누적 확인
    앱 종료 → 재실행 → 창이 커지지 않는지. settings.json의 windowBounds.width가 패널을 뺀 값이어야 한다
  7. 06b
    읽기 ↔ 편집 전환
    창 크기를 바꾼 채 문서 버튼으로 몇 번 오간 뒤 편집기가 제대로 그려지는지. 렌더링한 본문의 링크를 눌렀을 때 편집 창이 그 주소로 떠나지 않고 기본 브라우저가 뜨는지(createEditor()의 will-navigate)
  8. 07
    설정 손상 복구
    settings.json을 일부러 잘라 놓고 실행 → 콘솔에 복구 메시지가 뜨고 파일이 정상으로 되돌아오는지
  9. 08
    배포
    빌드 후 배포.bat 더블클릭. 종료 → 빌드 → 바탕화면 교체가 한 번에 진행된다

목록 패널 너비src/main/windows.js의 PANEL_WIDTH. 패널은 늘 붙어 있으므로 창 너비·최소 너비 계산에 항상 더해진다

알려진 한계

  • 패키지 앱 컨테이너 안에서 실행하면 데이터가 격리된다. MSIX로 설치된 앱(예: 개발 보조 도구)에서 이 앱을 실행하면 Windows가 %APPDATA% 쓰기를 %LOCALAPPDATA%\Packages\<패키지>\LocalCache\Roaming으로 돌린다. 컨테이너 안에서는 두 폴더가 겹쳐 보여 정상처럼 동작하지만, 밖에서는 그 메모가 보이지 않는다. 실제로 겪은 문제이고, 앱을 항상 탐색기에서 직접 실행하면 발생하지 않는다.
  • 코드 서명이 없다. 인터넷·메일로 전달하면 SmartScreen 경고가 뜬다. USB나 사내 공유 폴더로 건네면 뜨지 않는다
  • 자동 업데이트가 없다. 새 exe를 각자 바꿔 끼워야 한다
  • 목록이 전체 본문을 읽는다. 메모가 많아지면 느려진다 (07장)
  • 자동 실행은 배포한 PC에만 등록된다. deploy.ps1의 4단계가 시작프로그램 폴더에 --autostart 인자를 단 바로가기를 만들고, main.js가 그 인자를 보면 창을 띄우지 않고 트레이에만 올라간다(openInitialNote({ silent })). exe만 복사해 간 PC에서는 각자 등록해야 한다. portable 빌드라 app.setLoginItemSettings()는 쓰지 않았다. 그쪽이 레지스트리에 적는 process.execPath가 실행할 때마다 바뀌는 임시 폴더 경로이기 때문이다

미해결 · 미확인

  • 미측정 메모 개수에 따른 목록 열기 지연. 몇 개부터 체감되는지 확인하지 않았다
  • 미확인 즐겨찾기 순서가 settings.json 배열 순서에 의존한다. 파일을 손으로 고쳐 순서를 바꾸는 것이 의도된 사용법인지 정하지 않았다
  • 미확인 같은 초에 메모를 여러 개 만들 때 붙는 -1 접미사가 NOTE_ID_PATTERN과 맞는지는 코드상 일치하나 실제로 재현해 보지는 않았다
